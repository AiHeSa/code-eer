## 1. 目标

为代码健康度评估与代码质量审查提供语言原生的语法解析、代码结构提取，以及可扩展的语义分析能力。

- **首批支持语言**：覆盖 JS/TS、Python、Java、Go、Rust 五个语言方向。其中 JS 与 TS 共用同一个解析后端，但需分别完成独立验证；每个语言后端均支持独立安装、启用和验证，并通过统一接口供本项目调用。
- **核心技术栈与框架支持**：核心服务采用 TypeScript + Node.js 构建。首批前端框架支持 React 与 Vue 3，框架结构与底层语言结构通过统一的结果契约输出。

## 2. 已确认范围

| 语言方向 | 覆盖文件范围 | 首批共同交付能力（验收基线） | 进一步接入的能力（按需扩展） |
| --- | --- | --- | --- |
| **JS/TS** | `.js`、`.mjs`、`.cjs`、`.jsx`、`.ts`、`.mts`、`.cts`、`.tsx`（声明文件按项目配置处理） | 语法解析、结构与导入导出提取、语法诊断；采用新版 TypeScript API | 结合项目配置查询类型与符号信息 |
| **Python** | `.py`、`.pyi` | 语法解析、结构与导入提取、语法诊断 | 提取作用域与限定名称元数据；按需增加保留格式的代码修改能力 |
| **Java** | `.java` | 语法解析、声明与导入提取、语法诊断 | 在源码路径与依赖齐备时，解析符号、方法与类型 |
| **Go** | `.go`（区分普通源码与测试文件） | 语法解析、声明与导入提取、语法诊断 | 结合 Go Module、构建标签（build tags）和目标平台配置进行包加载与类型分析 |
| **Rust** | `.rs`（识别 Cargo 项目与 workspace） | 语法解析、声明与 `use`/`mod` 提取、语法诊断 | 按需查询定义、引用和类型；独立验证宏展开与条件编译（`cfg`）的分析范围 |

### 范围边界说明

- **基线能力与扩展能力区分**：“首批共同交付能力”是五个语言方向都必须达成的验收基线；“进一步接入的能力”按各语言后端的实际特性推进并单独标注状态，不强制要求五种语言具备完全相同的语义分析深度。
- **本阶段暂不纳入的目标**：首批聚焦单语言分析与前端框架结构提取，暂不要求跨语言调用关系、跨语言数据流或完整污点分析，也不强行将所有语言的原生 AST 合并为同一套底层语法树模型。`ast-grep` 与 `Tree-sitter` 仅保留为调研候选，不作为首批必需依赖。
- **前端框架输入范围**：涵盖 React 的 JSX/TSX 文件与 Vue 3 的 `.vue` 单文件组件（SFC）。关于脚本、模板解析及源码位置映射的具体要求，详见[框架支持需求](framework-support.md)。

## 3. 功能要求

### AST-F01：独立后端与环境识别

- **按语言独立启用**：每个语言方向均可单独启用；未安装其他语言的运行环境时，不影响已启用后端的正常使用。
- **环境与能力查询**：支持查询解析后端版本、目标语法版本、当前可用能力清单，以及缺失的运行环境依赖。
- **三类版本明确区分**：清晰区分“解析工具自身的运行时版本”、“被审查代码的语言版本”与“目标项目的构建配置”。
- **TypeScript 接口路线**：JS/TS 后端直接采用新版 TypeScript API 路线，不将旧版 API 兼容作为首批目标。

### AST-F02：文件与项目分析

- **输入形式**：支持传入单个文件、文件列表或项目根目录；首批以磁盘上的源码文件作为输入。
- **后端选择与多语言仓库**：依据显式指定的语言参数、文件扩展名和项目配置选择对应后端；多语言混合仓库可按语言分别执行分析，但不做跨语言语义推导。
- **路径过滤与测试开关**：支持配置包含路径、排除路径及是否分析测试文件；第三方依赖和构建产物默认不作为被审查源码。
- **依赖信息读取边界**：保留项目所需的依赖元数据供类型或符号解析使用——“不审查第三方依赖源码”不代表“禁止解析依赖的类型与符号声明”。

### AST-F03：结构事实提取与诊断

- **代码结构提取**：提取当前语言下的函数、类型、方法、模块及导入导出等结构事实，并完整保留源码位置与语言专属属性。
- **诊断信息返回**：默认返回语法解析诊断；当后端具备语义分析能力时，一并返回类型诊断与符号信息。
- **语法后端能力边界**：首批语法级后端不强制要求提供完整调用图、类型推断或自动修复功能。
- **与具体审查规则解耦**：具体的代码审查规则在独立需求中逐项定义；本轮重点验证提取出的结构数据能否被下游审查模块消费，暂不预先制定整套审查规则或健康度评分标准。

### AST-F04：执行状态与能力完整性可辨识

- **明确的执行状态**：清晰区分“全部完成（`completed`）”、“部分完成（`partial`）”、“失败（`failed`）”与“已取消（`cancelled`）”。
- **异常原因可识别**：对依赖缺失、语法版本不支持、解析失败、语义分析不可用、执行超时等情形提供可识别的状态或原因说明。
- **语义不可用时的降级处理**：当语义分析能力不可用时，保留已生成的有效语法结构结果，并将依赖语义能力的审查规则明确标记为“未执行”及具体原因。
- **避免“零问题即健康”的误判**：空的问题列表不能单独代表“代码健康”或“检查全部通过”；返回结果必须同时携带完成状态、诊断信息、运行错误及未执行项清单。

### AST-F05：统一调用契约与输出模型

- **多端共用核心后端**：CLI、MCP 服务与前端工作台均通过核心模块复用同一组语言后端。
- **调用结果可追溯**：每次调用结果均可追溯输入文件、后端版本、语言版本、生效配置及实际执行的能力项。
- **公共结构模型转换**：各语言和框架适配器负责将原生解析结果转换为公共结构模型，对外统一核心结构事实、诊断格式与源码位置，同时保留节点来源、语言专属字段及转换覆盖范围（无需强行统一底层原生 AST）。
- **三类问题分开表达**：将“代码审查问题”、“编译器/解析器诊断”与“工具自身运行错误”分开存放，避免混杂。

### AST-F06：安全执行与故障隔离

- **超时控制与故障隔离**：支持任务超时控制、主动取消，以及单个语言后端的故障隔离。
- **外部代码执行管控**：语法解析以静态读取源码为主；若涉及项目构建脚本、Rust `build.rs` 或过程宏（proc-macro）等可能执行外部代码的行为，必须通过显式运行配置加以控制。
- **依赖获取与源码解析分离**：缺少项目依赖时如实报告受限能力；依赖下载、项目构建流程与静态源码解析保持分开配置。

### AST-F07：版本锁定与验证记录

- **版本与支持范围锁定**：接入时锁定实际验证通过的工具、依赖库与运行时版本，并记录所支持的语法特性与项目配置范围。
- **JS/TS 新接口先行验证**：新版 TypeScript API 需先通过小型验证项目完成可行性验证，再推进完整接入。
- **预发布版本管理**：若使用预发布（pre-release）版本组件，须明确标注版本号与当前状态，并在版本升级后运行对应的兼容性回归用例。

## 4. 验收标准

- **五语言主流程跑通**：JS/TS、Python、Java、Go、Rust 五个方向均可独立跑通“读取源码 → 解析 → 输出结构事实与诊断”的完整流程。
- **JS/TS 专项覆盖**：JS 与 TS 分别覆盖普通模块及 JSX/TSX 用例，并针对锁定版本的新语法建立测试用例。
- **前端框架覆盖**：React 与 Vue 3 完成框架支持需求中定义的结构提取、异常输入处理及原始源码定位用例。
- **异常与多字节字符场景**：每种语言均覆盖正常源码、语法错误、文件缺失、配置或依赖缺失，以及包含中文、Emoji 等非 ASCII 字符的源码位置计算。
- **下游消费与源码回溯**：输出的结构结果包含足够支撑后续审查规则编写的信息，且所有结构节点均可准确定位回原始源码。
- **不支持能力如实反馈**：请求后端不支持的能力时明确返回原因，绝不将“未执行的规则”当成“检查通过”。
- **语义能力真实有效**：具备语义能力的后端需使用跨文件样例验证符号或类型查询；纯语法后端不得伪造此类语义结果。
- **单后端故障隔离**：单个语言后端不可用、崩溃或超时，不影响其他已启用后端的正常分析。
- **文档与可复现说明**：每个语言后端均配备可重复执行的运行说明与兼容性记录。
