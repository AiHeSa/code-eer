# 代码位置评分算法

- 日期：2026-11-07
- 标识：SCP-P / placement-evidence-1
- 状态：配置归属、导入导出及文件内角色候选已实现；职责适配和数值映射是后续实现规格。
- 依据：[原设计](../2026-11-06/scope-complexity-placement.md)、[采集契约](assessment-collection.md)

## 1. 模块配置及职责来源

模块边界按项目相对路径配置，不把 public、utils、common 等目录名直接当成职责证明。
示例见 [assessment.example.json](../../../config/assessment.example.json)：

```json
{
  "modules": [
    { "id": "feature", "root": "src/feature", "kind": "business", "entries": ["src/feature/index.ts"] },
    { "id": "shared", "root": "src/shared", "kind": "public", "entries": [] }
  ]
}
```

kind 为 public / business / unknown，描述职责而非访问权限。
entries 使用项目相对文件路径，只证明配置了文件入口，不证明文件内每个函数都是入口。
配置先做路径归一化和边界验证；重复 ID、等价根路径、越界入口和父目录穿越均拒绝。

一个文件命中多个模块时选择最长完整路径前缀；`src/a` 不匹配 `src/ab`。
无配置时保留 path、导入导出和 AST 框架候选，module.kind=unknown。

## 2. 关系与角色

以功能模块和选定关系类型为参照，建立声明、调用、导入导出、路由/组件等框架关系。
跨模块调用与模块内调用分别记录；外部消费者和动态入口属于覆盖边界。

| 角色 | 确认所需证据 | 不足时的结果 |
| --- | --- | --- |
| 公共入口 | public 模块契约、对外导出或显式入口、契约边界 | 入口候选 |
| 业务入口 | business 模块契约、路由/命令/事件入口、编排关系 | 入口候选 |
| 公共叶子 | public 职责契约、完整出边、原子能力职责 | 叶子候选 |
| 业务叶子 | business 职责契约、完整出边、局部业务职责 | 叶子候选 |
| 中间处理 | 上下游关系与明确的层次职责 | 中间候选 |

角色可以并存；一个文件可同时提供公共入口和内部叶子函数。
导出不等于根入口，没有已知调用方不证明没有消费者，零已知出边也不证明是叶子。

当前文件内候选算法：

1. 缺少细粒度语法或函数无实现体：unknown。
2. 存在未解析调用：unknown，输出相关调用 ID。
3. 无已知出边：leaf-candidate。
4. 有出边且无文件内已知调用方：entry-candidate。
5. 其他：intermediate-candidate。

所有这些 roleStatus 都是 candidate；真实角色确认还需要项目与框架关系。
React 组件事实通过 astFacts ID 关联，不把 JSX 自动改写成已解析的函数调用。

## 3. 职责适配算法

后续为每个模块建立版本化职责契约，包括：

- 允许依赖的模块/层、允许对外暴露的对象和允许使用的状态/IO 类别。
- 公共能力与业务概念的边界，以及入口、编排、叶子的职责规则。
- 输入校验、错误转换、资源责任及公共 API 的契约要求。

将 AST/语义事实映射到规则，而非按文件名或函数名打分：

1. 解析 import、re-export 和实际符号目标，识别模块依赖方向与被使用的对象。
2. 识别输入边界、外部 IO、共享状态、业务依赖、流程编排及原子计算等职责证据。
3. 将对象的候选角色与模块契约匹配；角色未确认时保留 unknown。
4. 对每项规则输出 satisfied / violated / unknown / not-applicable，以及位置和依据。
5. 同一职责问题使用稳定规则 ID 去重，聚合时保留所属对象和范围。

示例规则规格：

| 规则 ID | 对应角色 | 违例证据 |
| --- | --- | --- |
| P-DEPENDENCY-BOUNDARY | 所有 | 已解析依赖违反模块允许方向 |
| P-PUBLIC-BUSINESS-COUPLING | 公共能力 | 公共能力依赖契约禁止的业务模块/状态 |
| P-ENTRY-CONTRACT | 公共/业务入口 | 已声明的输入或错误契约缺失 |
| P-LEAF-RESPONSIBILITY | 公共/业务叶子 | 叶子执行契约禁止的编排、IO 或状态行为 |
| P-ROLE-MIXING | 所有 | 同一对象承担契约明确互斥的职责 |

规则需要能力覆盖和契约前提。未看到校验调用不能直接判定缺少输入校验，
跨框架中间件和类型契约仍可能承担此职责。无法证明时输出 unknown。

## 4. 评分映射

设适用且证据充分的职责规则集合为 R，各规则权重为 w_i，违例严重度为 v_i∈[0,1]：

```text
已知规则的条件分 P_known = 100 × (1 − Σ(w_i × v_i) / Σw_i)
完整 P = 仅当所有必需职责规则、角色和模块边界有效时采用 P_known
```

没有适用规则时为 not-applicable；必需规则未知时完整 P 待定，不能丢弃未知规则后重归一化成高分。
权重、严重度映射、角色确认阈值和聚合方式待校准，当前 score=null。

位置项只计职责适配：调用次数、复用数量、影响方法/文件/模块数及链路长度归作用域项；
执行成本归复杂度项。跨模块依赖只有违反职责契约时计位置违例，不按复用规模扣分。
同一原始关系可以提供不同事实依据，但同一质量问题只归属一个扣分条目。

## 5. 验收

使用公共叶子、业务入口、中间编排、混合职责文件、合法跨模块复用、反向依赖、
未解析动态调用、嵌套模块、路径前缀碰撞、框架入口和重导出样例。
对目录改名但契约与关系未变的样例，原始职责分应不变；对复用次数变化而职责未变的样例，
位置项不应重复变化。当前集成测试验证模块最长边界、入口配置和角色候选的保守输出。
