# 抗急性劣化的静态与语义信号设计

- 日期：2026-11-07
- 需求：[REQ-HEALTH-001](../../requirements/code-review/evolutionary-resilience.md)、[提示词双入口与分发](../../requirements/prompts/entry-routing.md)
- 关联：[Prompts 双入口设计](prompt-entry-routing.md)、[三项评分设计](../2026-11-06/scope-complexity-placement.md)、[位置加权 v1](position-weighting.md)、[采集契约](assessment-collection.md)
- 状态：研究与设计规格，用于指导后续 `prompts/requirements/`（`inject` / `check` 阶段投影）与增量审阅能力建设。

本文中的结构信号与反向约束是候选研究材料，具体执行以 `prompts/requirements/` 的条件和例外为准。单消费方、链路增长或内部判空不能独立证明违规；明确的职责隔离、规模约束和合法可空契约须保留。未实现检测或证据不足时按三态预筛契约记为 unknown，不能静默通过。

## 1. 核心设计目标与模型偏好纠偏

大模型在生成代码时存在两个显著的训练偏好（Bias）：
1. **教科书式过度分层偏好**：倾向于展示复杂的企业级目录结构（动辄拆分 Interface / Factory / Helper 多文件），无视仓库已有的轻量单文件先例。
2. **防御性免责偏好**：害怕运行报错而习惯性添加冗余判空、默认值兜底与静默 `try-catch`，掩盖本应暴露的契约违例。

若在编码前泛泛要求“写出高质量、可扩展的代码”，反而会触发模型的过度设计本能。因此，本方案将“抗急性劣化 + 内部 Fail-Fast + 最小作用链路”转化为与 `prompts/` 双入口咬合的两阶段信号体系：
- **阶段一（`inject` 编码前预防）**：用反向约束遏制模型过度设计与过度防御本能。
- **阶段二（`check` 编码后审阅）**：基于改动前后快照差分（Before / After Delta）与最小链路反事实推演，精准识别劣化斜率与跨文件链路膨胀。

## 2. 阶段一：编码前预防信号（`inject` 阶段四道反向约束）

在模型动笔前，前置指令聚焦以下高杠杆反向约束：

| 预防维度 | 编码前核心指令（`inject` 核心注入点） | 纠偏的典型反模式 |
| --- | --- | --- |
| **1. 先例对齐优先于通用模式** | 动手前先对齐仓库中同类功能的既有实现粒度；若既有实现均为单文件局部纯函数，严禁自立门户引入新目录或跨文件抽象层 | 无视先例：在轻量函数式模块中突然引入一套多层 Class/Factory/Adapter 跨文件结构 |
| **2. 作用域由内向外升级制** | 遵循“局部块/IIFE → 文件内纯函数 → 同模块跨文件 → 跨模块公共”的升级举证责任；**能单文件闭环绝不新建文件或新增 `export`**，仅当存在**当前真实可见的第二个消费方**时才允许跨文件抽离 | 假性扩展（Speculative Generality）：以“预留未来扩展空间”为借口，把单文件可解决的问题拆成多文件调用链 |
| **3. 边界窄化 + 内部信任** | 明确区分系统入口（Entry）与内部节点（Intermediate / Leaf）；仅在入口校验外部输入，**内部函数直接信任参数契约，严禁写冗余判空、伪造兜底默认值或静默 `catch`** | 过度防御：内部叶子函数层层 `if (!arg) return defaultVal`，拦截并掩盖上游破坏契约的真实 Bug |
| **4. 数据/表驱动替代分支堆叠** | 严禁往既有 `if-else` / `switch` 链上机械追加平行分支，或给函数签名增加布尔控制参数（Flag Argument）；同类扩展优先收敛为映射表或独立纯函数 | 分支爆炸：每次迭代顺手追加 `else if` 与布尔开关，导致主干函数迅速突破 40 行与多层嵌套 |
| **5. 循环与递归的显式成本意识** | 循环与递归内严禁混入隐式高开销调用（如重复线性查找、深拷贝、未受控 I/O）；高频查找优先预处理为索引结构（Map/Set） | 隐式退化：在循环内调用看似无害的辅助遍历函数，导致整体退化为 $O(n^2)$ |

## 3. 阶段二：编码后增量劣化审阅（`check` 阶段前后对比信号）

编码结束后的审阅严禁孤立对新文件做静态打分（拆成多个碎文件后，单文件行数与圈复杂度往往具有欺骗性的高分），必须基于 **Before / After 快照差分（Delta）** 与 **最小更优链路审计** 切入。

### 3.1 静态增量劣化信号（Internal AST / Semantics Delta）

结合现有 [候选评分策略](scoring-policy-v0.md) 中作用域链路扣分公式 $D_{\text{raw}} = 2\log_2(1+M) + 4\log_2(1+F) + 6\log_2(1+U) + 1.5L + 8W$（跨文件 $F$ 与跨模块 $U$ 惩罚权重远高于单文件内方法 $M$），重点捕获四类差分信号：

| 评估切面 | 静态差分指标（Before → After） | 待复核的急性劣化与过度设计候选 |
| --- | --- | --- |
| **1. 存量方法复杂度放大（`ΔC`）** | 既有函数的循环嵌套深度 $\Delta d$、分支数 $\Delta b$、成本上界比 $\Delta(T/B)$、函数行数 $\Delta \text{LOC}$ | 修改既有函数后，最大嵌套深度增加、时间/空间增长阶跃迁（如 $O(n) \to O(n^2)$），或单函数逼近/突破 40 行限制 |
| **2. 存量对象作用链路增长（`ΔS`）** | 既有绑定的作用域档位变化、受影响方法 $\Delta M$、受影响文件 $\Delta F$、受影响模块 $\Delta U$、最长链路 $\Delta L$、状态传播 $\Delta W$ | 1. 局部变量被提升为模块顶层 `global` 绑定（基础分从 `70` 跌至 `45` 且放大 $W$）；<br>2. 既有纯函数因塞入外部状态读写而丧失 `pure` 加成；<br>3. 局部改动导致波及文件数 $\Delta F$ 与链路深度 $\Delta L$ 异常增长 |
| **3. 跨文件链路膨胀候选** | 新增跨文件导出符号的**调用图入度（In-degree）**、中间节点的计算密度（有效运算语句 / 透传语句比） | 1. **单消费者跨文件导出（Single-Consumer Export）**：调用关系完整时，新增导出只有一个消费者，需进一步核查职责隔离、依赖方向或规模约束收益；<br>2. **纯透传中间层（Pass-through Node）**：新增函数仅转发参数，仍需核查其是否承担合法协议或生命周期边界 |
| **4. 位置职责与 Fail-Fast 侵蚀（`ΔP`）** | 叶子节点新增外部调用出边、公共模块新增业务导入、内部节点新增吞错/兜底分支 | 原本纯粹的 `leaf` 混入外部调用退化为 `intermediate`；或内部函数新增空 `catch`、对非空契约参数做 `??` 默认兜底 |

### 3.2 语义与最小更优链路审阅信号（LLM Counterfactual Review）

将静态分析捕获的 $\Delta F$、“入度为 1 的新增跨文件导出”以及“同模块既有同类实现代码”输入审阅模型，重点执行三项反事实推演（Counterfactual Audit）：

| 审阅切入点 | 核心反事实追问（`check` 阶段 Prompt 切入点） | 典型劣化判例与重构导向 |
| --- | --- | --- |
| **1. 可折叠性检验**<br>*(Collapsibility Test)* | “如果把本次新增的跨文件调用直接内联/收敛回调用方所在的单文件（用局部纯函数或 IIFE 隔离），是否能消除 $\Delta F$ 并缩短调用链 $\Delta L$，且完全不损失可读性？” | **判例**：为单一模块内部逻辑新建 `helper/service` 文件（入度 = 1）。<br>**重构**：折叠回原文件局部纯函数，令 $\Delta F \to 0$ |
| **2. 先例偏离检验**<br>*(Precedent Deviation)* | “对比仓库中此前同类功能的实现方式，本次代码为何偏离既有的轻量组织粒度？多出来的跨文件抽象层有当前已证实的收益吗？” | **判例**：同类能力均在单文件内完成，本次却拆出多层包装。<br>**重构**：对齐既有先例粒度，砍掉无消费者的预留扩展层 |
| **3. 三次顺延劣化推演**<br>*(3x Trend Extrapolation)* | “若后续开发者完全照搬本次写法再迭代 3 个同类需求，该模块会发生分支爆炸、散弹枪修改还是文件碎片化？” | **判例**：在 3 个文件各加一个同构 `if (kind === 'x')` 或每次新建一套跨文件包装。<br>**重构**：收敛为单文件内的表驱动映射或内聚纯函数 |
| **4. 内部过度防御剥离**<br>*(Fail-Fast Audit)* | “新增的判空、`try-catch` 或默认值兜底是在处理真实的外部边界输入，还是在掩盖上游破坏契约的内部错误？” | **判例**：内部计算函数对必传字段做 `val ?? 0` 静默兜底。<br>**重构**：移除内部冗余兜底，恢复契约直通与快速失败 |
