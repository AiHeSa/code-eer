# 原型豁免、改动授权与审查流程

## prototype-exemptions
demo／原型仅在用户或项目约定明确标记的文件／目录、规则范围内临时豁免；不因目录名含 demo、代码简单或赶时间自行认定豁免，也不扩大到测试、安全或其他项目要求。
启用豁免前，在目标项目的 `.code-eer/prompts/exemptions.json` 记录 `format: 1` 和 `exemptions` 列表；逐项包含 `id`、项目相对 `paths`（精确文件或目录）、`ruleIds`、`reason`、授权来源 `authority`、`status` 和状态变更 `history`。没有豁免时无需创建文件，不修改安装清单来记录运行状态。
只有 `status=prototype` 的明确范围跳过指定规则的注入和审查；其他对象、规则继续照常处理。跳过项记为 exempted，不记作 clear／satisfied；结果披露豁免范围，整体覆盖保留 partial。

## graduation
状态路径为 `prototype → pending-review → reviewed`，在每次相关任务开始和收尾时核对：
用户决定保留原型属于源码审查任务，即使没有源码改动也执行状态核对和补审，不归入纯文档任务排除项。
1. 正式模块引用原型代码，或用户明确表示“保留／正式使用”时，立即记录触发来源并转为 pending-review；不等用户再次确认，不自动把引用方加入豁免。
2. pending-review 立即停止豁免，按当前源码、依赖和规则版本补跑原先跳过规则的 eer-check；范围包含原型代码的适用对象及正式接入边界，不能只审查毕业这一轮的 diff。
3. 记录检查范围、源码／规则版本、证据和结论引用。补审证据齐全后记为 reviewed；reviewed 仅表示补审完成，不表示没有问题。缺基线或依赖证据时保留 pending-review 与 unknown／partial，不能直接销账。
4. reviewed 后进入常规规则流程，不恢复原型豁免；改名、移动或新会话不重置状态。修改路径时保留原有身份和历史，不让同一对象通过新增或重叠记录重新获得豁免。

由执行代理依据用户声明和可取得的依赖证据维护状态；当前没有自动引用检测器、账本读写器或补审执行器。无法确认已有豁免范围或毕业状态时保留 unknown／partial，并按正常规则处理，不默认延续豁免。只核对本任务涉及的豁免和接入边界，不因此发起无关全仓扫描。

## authorization
大改应先确认是否已在用户授权范围内；超出范围、引入未约定的架构调整或改变已约定的公开接口／兼容性时，先给出具体范围、行为影响和方案，由用户决定是否实施。
已有明确重构授权覆盖的拆文件、抽象调整和其他常规实现选择自主完成，不重复索要同一授权，也不为每个实现选择反复论证。
用户确认只解决是否实施，不构成质量审查豁免；改完后照常执行 eer-check。审查建议也不扩大修改授权。

## judgment-and-evidence
接受模糊规则在不同会话中的合理判断差异；不要求为假想分歧追加一致性规则或反复请求用户裁决。
结论仍须引用当前对象的源码、所选同类先例或输入契约等实际依据，区分事实与推断；缺少依据标记 unknown／partial，不输出 full pass。实际出现反复分歧时再针对案例补规则。
